# Поток событий и параметры

Рабочий пример на все возможности — `example.conf` рядом. Здесь разбирается,
**что именно течёт по конвейеру**: как строка SQL превращается в событие на
входе и во что это событие превращается на выходе. Все примеры ниже — реальный
вывод со стенда `test/stand`, не выдуманный.

Сняты они не за один запуск, поэтому между разделами меняются имя ноды
(`hostName()` — это идентификатор контейнера) и метки времени. Внутри одного
разбора данные всегда из одного прогона: если сказано «та же строка» или «тот
же тик» — так и есть.

Справочник по самим плагинам — `../plugins/README.md`.

## Событие бывает двух видов

fluent-bit переносит не «строки», а **события**. Их ровно два вида, и они
несовместимы: выход, принимающий одно, не примет другое.

**Запись (log)** — пара «время + объект»:

```
время: 2026-08-26 10:51:20.453106
тело:  {"instance": "436c24c01cd8", "database": "demo", "table": "pg_events", "rows": 50000}
```

**Метрика (metric)** — имя, метки, число и время:

```
clickhouse_parts_rows{instance="436c24c01cd8", database="demo", table="pg_events"} 50000
```

Разница принципиальная. Запись хранит **что произошло** — у неё произвольный
набор полей, включая тексты. Метрика хранит **сколько** — одно число, у которого
есть имя и метки, и она пригодна для `rate()`, графиков и алертов.

Отсюда правило тегов: `metric.*` — метрики, `log.*` — записи. `prometheus_exporter`
принимает только метрики, `elasticsearch` и `stdout` — только записи; наши
`postgres` и `clickhouse` на выходе принимают и то, и другое.

## Тег: где он живёт и как по нему матчат

У события есть третья часть, которой не видно ни в одном примере ниже, — сам
**тег**. Он не поле записи и не метка метрики: это строка, приклеенная к пачке
рядом с данными, и нужна она ровно для одного — решить, в какие выходы пачку
отдать.

Ставит тег вход, параметром `Tag`. Не задан — fluent-bit придумает сам, из
имени плагина и его номера:

```
$ fluent-bit -i dummy -o stdout
[0] dummy.0: [[1787741285.448897045, {}], {"message"=>"dummy"}]
```

Увидеть тег можно у `stdout` в формате по умолчанию. Вот запись про
`pg_events`, напечатанная двумя выходами в один и тот же тик — сначала
`Format msgpack`, потом `Format json_lines`:

```
[1] log.ch.parts: [[1787741480.453105829, {}], {"instance"=>"436c24c01cd8", ...}]
 ^   ^               ^                     ^     ^
 |   |               |                     |     тело записи
 |   |               |                     метаданные события, обычно пустые
 |   |               время события
 |   тег
 номер записи внутри пачки

{"date":1787741480.453106,"instance":"436c24c01cd8","database":"demo", ...}
```

Главное здесь — вторая строка: в `json_lines` тега **нет**. Он не потерялся,
его просто негде показать, потому что он никогда не был частью тела. Все
остальные примеры в этом файле сняты через `json_lines`, поэтому тега в них и
не видно.

У метрик то же самое, только заметнее. Та же пачка, ушедшая под тегом
`metric.ch.parts`, печатается так:

```
2026-08-26T10:51:20.453105829Z clickhouse_parts_parts{instance="436c24c01cd8",database="demo",table="pg_events"} = 2
```

От тега в выводе не осталось ничего — метрика состоит из имени, меток,
значения и времени. Что тег всё-таки был, доказывает сам факт этой строки: её
напечатал выход с `Match metric.ch.parts`.

**Как по тегу матчат.** `Match` сравнивает строку тега с шаблоном: `*` — что
угодно, `log.*` — всё с этим префиксом, `log.ch.parts` — точное совпадение;
`Match_Regex` — то же регулярным выражением. Так же матчат и фильтры.

Важная деталь, из-за которой примеры выше вообще возможны: пачка уходит **во
все** подходящие выходы, а не в первый попавшийся. В этом прогоне метрики
одновременно приняли `prometheus_exporter` с `Match metric.*` и `stdout` с
`Match metric.ch.parts` — 18 рядов в экспортёре и те же значения в логе
контейнера. Записи в `prometheus_exporter` при этом не попали: их тег
начинается с `log.`.

Отсюда же смысл `Metrics_Tag` при `Mode both`: вход отдаёт два несовместимых
вида событий, и развести их можно только тегом — записи уходят под `Tag`,
метрики под `Metrics_Tag`.

# Как выглядит поток на входе

## Строка SQL → запись

Всё, что показано ниже, приехало вот из этого блока — он взят из
`test/stand/fluent-bit.conf` дословно, вместе с `${…}` из окружения:

```ini
[INPUT]
    Name              clickhouse
    Tag               log.ch.parts
    Mode              both
    Metrics_Tag       metric.ch.parts
    Metric_Prefix     clickhouse_parts
    Label_Fields      database, table
    Targets           ${CH_TARGETS}
    User              ${CH_USER}
    Password          ${CH_PASSWORD}
    Query_File        /usr/local/share/fluent-bit/queries/ch/parts.sql
    Interval_Sec      5
```

`Mode both` — это «отдай и записи, и метрики», поэтому один и тот же блок
кормит и текущий раздел, и следующий: записи уходят под `Tag`, метрики под
`Metrics_Tag`. Остальные параметры разбираются там, где до них дойдёт речь;
полный перечень — во второй половине этого файла.

Запрос обычный, никакой разметки в нём нет — это `queries/ch/parts.sql`
целиком, как его читает плагин (`Query_File` выше):

```sql
SELECT
    hostName() AS instance,
    database,
    table,
    count()                      AS parts,
    sum(rows)                    AS rows,
    sum(bytes_on_disk)           AS bytes_on_disk,
    sum(data_uncompressed_bytes) AS uncompressed_bytes,
    max(level)                   AS max_level,
    uniqExact(partition)         AS partitions
FROM system.parts
WHERE active AND database NOT IN ('system', 'INFORMATION_SCHEMA', 'information_schema')
GROUP BY database, table
ORDER BY bytes_on_disk DESC
LIMIT 200
FORMAT JSONEachRow
```

Тот же текст, отданный `clickhouse client` вместо плагина, отвечает таблицей:

```
   ┌─instance─────┬─database─┬─table─────┬─parts─┬───rows─┬─bytes_on_disk─┬─uncompressed_bytes─┬─max_level─┬─partitions─┐
1. │ 436c24c01cd8 │ demo     │ events    │     5 │ 800000 │       3937425 │           68002905 │         1 │          2 │
2. │ 436c24c01cd8 │ demo     │ pg_events │     2 │  50000 │        220800 │            5090475 │         0 │          1 │
3. │ 436c24c01cd8 │ demo     │ nginx_agg │     4 │     13 │          2873 │                455 │        97 │          1 │
   └──────────────┴──────────┴───────────┴───────┴────────┴───────────────┴────────────────────┴───────────┴────────────┘
```

Плагин отдаёт **по событию на строку** — три строки, три события. Столбцы
становятся полями, имена сохраняются; вот строка про `pg_events`, как её
напечатал `stdout`:

```json
{"date":1787741480.453106,"instance":"436c24c01cd8","database":"demo","table":"pg_events","parts":2,"rows":50000,"bytes_on_disk":220800,"uncompressed_bytes":5090475,"max_level":0,"partitions":1}
```

`date` — это время события, оно живёт отдельно от тела; в `stdout` с
`Format json_lines` его печатают первым полем. Типы не теряются: числа приезжают
числами, `NULL` — `null`, `json`-столбец PostgreSQL — вложенным объектом.

## Та же строка → метрики

Ни запрос, ни блок `[INPUT]` не меняются — это всё тот же вход со страницы
выше. Работают три его строки, до которых мы там не дошли:

```ini
    Mode              both            # с Mode metrics были бы только метрики
    Metric_Prefix     clickhouse_parts
    Label_Fields      database, table
```

`Mode` решает, что отдавать (`logs`, `metrics` или `both`), `Metric_Prefix` —
начало имени, `Label_Fields` — какие столбцы считать метками.

Из каждого числового столбца получается gauge `<Metric_Prefix>_<столбец>`, а
метка `instance` добавляется сама. Строка про `pg_events` — та же, что выше
приехала записью, — разворачивается так:

```
clickhouse_parts_parts{instance="436c24c01cd8",database="demo",table="pg_events"} 2
clickhouse_parts_rows{instance="436c24c01cd8",database="demo",table="pg_events"} 50000
clickhouse_parts_bytes_on_disk{instance="436c24c01cd8",database="demo",table="pg_events"} 220800
clickhouse_parts_uncompressed_bytes{instance="436c24c01cd8",database="demo",table="pg_events"} 5090475
clickhouse_parts_max_level{instance="436c24c01cd8",database="demo",table="pg_events"} 0
clickhouse_parts_partitions{instance="436c24c01cd8",database="demo",table="pg_events"} 1
```

Числа те же, что в записи выше, — это буквально та же строка результата, просто
развёрнутая иначе. Шесть числовых столбцов дают шесть метрик, а три строки
таблицы — восемнадцать (`curl :2021/metrics | grep -c '^clickhouse_parts_'`
отвечает `18`): писать по блоку конфигурации на метрику не нужно. На запросе
вроде `queries/pg/database.sql`, где числовых столбцов два десятка, экономия та
же, только заметнее.

Строки, `NULL` и вложенные объекты в метрики не попадают: их место либо в
метке, либо в записи. Здесь метками стали `database` и `table`, а `instance`
плагин добавил сам.

Обратная задача — не «взять все числовые столбцы», а «взять только эти» —
решается `Value_Fields`. В блоке выше его нет, зато есть в соседнем входе того
же стенда, где числовых столбцов много, а метриками должны стать пять:

```ini
[INPUT]
    Name              postgres
    Tag               metric.pg.tables
    Mode              metrics
    Metric_Prefix     pg_table
    Label_Fields      schema, table
    Value_Fields      n_live_tup, n_dead_tup, seq_scan, idx_scan, total_bytes
    Query_File        /usr/local/share/fluent-bit/queries/pg/tables.sql
    Interval_Sec      5
```

Список стоит задавать явно всюду, где запрос отдаёт «широкую» строку: иначе
метрикой станет случайное число вроде `pid` в `pg_stat_activity`.

## Журнал с курсором → поток событий

Другой вход того же стенда, и здесь важен каждый параметр:

```ini
[INPUT]
    Name              clickhouse
    Tag               log.ch.part_log
    Targets           ${CH_TARGETS}
    User              ${CH_USER}
    Password          ${CH_PASSWORD}
    Query_File        /usr/local/share/fluent-bit/queries/ch/part_log.sql
    Cursor_Field      event_ts
    Cursor_File       /var/lib/fluent-bit/ch-part_log
    Cursor_Type       datetime64
    Cursor_Default    now() - INTERVAL 30 SECOND
    Time_Field        event_ts
    Interval_Sec      5
```

Запрос, на который ссылается `Query_File`, целиком (`queries/ch/part_log.sql`):

```sql
SELECT
    hostName()  AS instance,
    toString(event_time_microseconds) AS event_ts,
    toString(event_type)    AS event_type,
    toString(merge_reason)  AS merge_reason,
    database,
    table,
    part_name,
    partition,
    part_type,
    rows,
    size_in_bytes,
    duration_ms,
    merged_from,
    error
FROM system.part_log
WHERE event_time_microseconds > {CURSOR}
  AND database NOT IN ('system', 'INFORMATION_SCHEMA', 'information_schema')
ORDER BY event_time_microseconds
LIMIT 2000
FORMAT JSONEachRow
```

Дальше разбирается, как этот запрос и блок выше работают вместе.

`Mode` не задан — значит `logs`, только записи. Зато появились пять новых
параметров, и дальше речь именно о них: `Cursor_Field` (что считать отметкой),
`Cursor_File` (где её хранить между перезапусками), `Cursor_Type` (в каком виде
подставлять в запрос), `Cursor_Default` (чем подставить на первом запросе) и
`Time_Field` (откуда брать время события).

Две строки из пяти — `Cursor_Type` и `Cursor_Default` — выписаны своими
значениями по умолчанию. Их можно молча убрать, поведение не изменится; в
стенде они стоят явно именно затем, чтобы было видно, что подстановкой
управляют, а не она «просто случается».

У запроса из `Query_File` есть подстановка `{CURSOR}` — место, куда плагин
ставит отметку, до которой дочитал в прошлый раз. Какой столбец ответа этой
отметкой считать, в самом SQL не написано: это и есть `Cursor_Field event_ts`
из блока выше.

Пустой `{CURSOR}` не бывает никогда: подставлять нечего только на самом первом
запросе, и там вместо отметки идёт `Cursor_Default` — в блоке выше это
`now() - INTERVAL 30 SECOND`, то есть «всё за последние полминуты». Значение
совпадает с умолчанием ClickHouse-входа; проверить, что у параметра в
умолчании, всегда можно так:
`fluent-bit -e …/flb-in_clickhouse.so -i clickhouse -h`. Так что условие в
`WHERE` рендерится всегда, и запрос выше — рабочий с первого тика.

Тонкость, которая сразу отвечает на «а если столбец не время»: `Cursor_Default`
— это не значение, а **кусок SQL**, он вставляется в запрос дословно. Поэтому
умолчание годится ровно для временно́го столбца: для курсора по `id bigint`
там должно стоять `Cursor_Default 0`. Полные правила — в разделе
[«Как рендерится `{CURSOR}`»](#как-рендерится-cursor).

```json
{"date":1787741402.452413,"instance":"436c24c01cd8","event_ts":"2026-08-26 10:50:02.452413","event_type":"NewPart","merge_reason":"NotAMerge","database":"demo","table":"nginx_agg","part_name":"all_348_348_1","partition":"tuple()","part_type":"Compact","rows":1,"size_in_bytes":682,"duration_ms":0,"merged_from":[],"error":0}
```

Вот что происходит с `{CURSOR}` вокруг этой пачки. Первый запрос ушёл с
`Cursor_Default`, то есть условие выглядело так:

```sql
WHERE event_time_microseconds > now() - INTERVAL 30 SECOND
```

Пришедшие строки плагин не только отдаёт в конвейер, но и просматривает: из
столбца `event_ts` он запоминает **наибольшее** значение по этой пачке — по
каждому серверу из `Targets` своё. Пустая пачка отметку не двигает. Пусть
наибольшей в пачке оказалась показанная выше строка — тогда следующий запрос
через `Interval_Sec` уедет таким:

```sql
WHERE event_time_microseconds > toDateTime64('2026-08-26 10:50:02.452413', 6)
```

Обёртка `toDateTime64(…)` — работа строки `Cursor_Type datetime64` из блока.
Она рассчитана на журнал по времени, и для курсора по возрастающему `id` обе
строки надо менять:

```ini
    Cursor_Field      id
    Cursor_Type       number      # иначе отметка уедет в toDateTime64(…)
    Cursor_Default    0           # иначе на первом запросе будет now() - INTERVAL …
```

Без первой из них запрос упадёт: отметка `9` уедет в `toDateTime64('9', 6)`, а
это уже не число. Вот что на такое сравнение отвечает сам сервер (проверено
`clickhouse local`, отсюда и синтетическое выражение в тексте ошибки — плагин
подставил бы ваш `id`):

```
Code: 41. DB::Exception: Cannot parse DateTime: Cannot parse DateTime64(6)
from String: In scope SELECT toUInt64(10) > toDateTime64('9', 6).
(CANNOT_PARSE_DATETIME)
```

Отдельно про `Cursor_File`. Без него отметка живёт только в памяти процесса:
перезапуск — и она потеряна, `{CURSOR}` снова заменяется на `Cursor_Default`,
а полминуты журнала приезжают повторно. `Cursor_File` хранит **саму отметку** —
последнее увиденное значение `Cursor_Field`, — и хранит её текстом, как есть.

Путь из конфигурации — это не имя файла, а **основа**: к нему дописывается
`.<host>-<port>`, потому что у каждого сервера из `Targets` отметка своя и
общий файл затирал бы соседний. Из `Cursor_File /var/lib/fluent-bit/ch-part_log`
на стенде получилось вот что:

```
$ ls -l /var/lib/fluent-bit/
-rw-r--r-- 1 root root 26 авг 26 11:50 ch-part_log.clickhouse-8123

$ cat /var/lib/fluent-bit/ch-part_log.clickhouse-8123
2026-08-26 11:50:43.454189
```

Двадцать шесть байт — ровно то значение, которое на следующем тике уедет
внутрь `toDateTime64(…)`. При старте плагин читает этот файл, и журнал
продолжается с того места, где остановился.

Отсюда же пара `ORDER BY` + `LIMIT` в запросе. Отметка двигается на максимум по
пачке, поэтому всё, что меньше максимума, но в пачку не попало, потеряно
навсегда. С `ORDER BY` по столбцу отметки обрезанный `LIMIT`-ом хвост — это
ровно самые поздние события, и они приедут следующим запросом. Без `ORDER BY`
сервер вернул бы произвольные 2000 строк, курсор прыгнул бы на максимум из них,
а остальное журнал бы не увидел.

Теперь вернитесь к записи выше и посмотрите на два её поля:

```json
{"date":1787741402.452413, … "event_ts":"2026-08-26 10:50:02.452413", …}
```

Выглядят они по-разному, потому что это разные вещи. `event_ts` — обычное
поле тела, строка ровно в том виде, в каком её отдал ClickHouse. `date` —
время самого события, оно лежит вне тела (см. разбор msgpack в начале файла), и
`stdout` печатает его секундами эпохи.

Значение при этом одно и то же:

```
1787741402.452413  →  2026-08-26 10:50:02.452413 UTC
```

Это и есть работа `Time_Field event_ts`: плагин разобрал строку из столбца и
поставил её временем события. Без этой строки в конфигурации `date` показывал
бы момент опроса — на секунды позже, а при отставании журнала и на минуты, — и
порядок событий у получателя разъехался бы с порядком в журнале.

`Cursor_Field` и `Time_Field` здесь указывают на один столбец, но делают
разное: первый решает, что спросить в следующий раз, второй — какое время
поставить событию.

## Насос pg2ch → только отчёт

Третий вход стенда устроен иначе: у него два адреса, а не один, и запроса к
приёмнику два — сам `Query` и `Cursor_Query`, которым насос спрашивает у
ClickHouse, докуда долил в прошлый раз:

```ini
[INPUT]
    Name              pg2ch
    Tag               log.pump.events
    Pg_Target         ${PG_TARGETS}
    Pg_User           ${PG_USER}
    Pg_Password       ${PG_PASSWORD}
    Pg_Database       ${PG_DATABASE}
    Ch_Target         ${CH_TARGETS}
    Ch_User           ${CH_USER}
    Ch_Password       ${CH_PASSWORD}
    Ch_Database       demo
    Ch_Table          pg_events
    Query             SELECT id, ts AT TIME ZONE 'UTC', kind, payload FROM demo_events WHERE id > {CURSOR} ORDER BY id
    Cursor_Query      SELECT coalesce(max(id), 0) FROM demo.pg_events
    Batch_Bytes       4M
    Interval_Sec      5
```

Обратите внимание: `Cursor_Field` и `Cursor_File` здесь не нужны — отметку не
хранит ни плагин, ни диск, её каждый раз заново спрашивают у целевой таблицы.
Поэтому перезапуск ничего не теряет и не задваивает, и поэтому же перегон
таблиц отдан насосу, а не обычному входу с курсором.

Данные `pg2ch` гонит мимо конвейера (PG `COPY` → CH `INSERT` напрямую), поэтому
в поток попадает одна запись на прогон:

```json
{"date":1787741435.491328,"table":"pg_events","status":"ok","rows":50000,"bytes":5179369,"batches":2,"duration_ms":42.415757,"cursor":"0","error":""}
```

Неудачный прогон выглядит так же, но со `status` и `error` — по ним удобно
делать алерт:

```json
{"date":1787731225.450684,"table":"pg_events","status":"error","rows":0,"bytes":0,"batches":0,"duration_ms":0.0,"cursor":"0","error":"copy failed to start"}
```

# Как выглядит поток на выходе

На выходе события накапливаются в **пачку** (её размер задаёт не конфигурация,
а то, сколько успело накопиться за `Flush`), и вся пачка уезжает **одним**
запросом.

## Записи → ClickHouse

Конфигурация:

```ini
[OUTPUT]
    Name     clickhouse
    Match    log.nginx
    Host     ch-1
    Database logs
    Query    INSERT INTO nginx_minute SELECT toStartOfMinute(timestamp) AS minute, host, status, count() AS hits, sum(bytes) AS bytes FROM input('timestamp DateTime64(6), host String, status UInt16, bytes UInt64') GROUP BY minute, host, status
```

Вот что плагин **реально отправляет** (поймано HTTP-ловушкой). Запрос уезжает
в URL, данные — телом:

```
POST /?query=INSERT INTO nginx_minute SELECT toStartOfMinute(timestamp) AS minute,
     host, status, count() AS hits, sum(bytes) AS bytes
     FROM input('timestamp DateTime64(6), host String, status UInt16, bytes UInt64')
     GROUP BY minute, host, status FORMAT JSONEachRow
     &database=logs&input_format_skip_unknown_fields=1

{"timestamp":"2026-08-26 08:01:02.396999","host":"web-1","status":200,"bytes":1024,"path":"/api/v1/users"}
{"timestamp":"2026-08-26 08:01:02.448897","host":"web-1","status":200,"bytes":1024,"path":"/api/v1/users"}
{"timestamp":"2026-08-26 08:01:02.948881","host":"web-1","status":200,"bytes":1024,"path":"/api/v1/users"}
```

Что здесь видно:

- значения **не попадают в текст запроса** — они в теле, разбирает их сервер.
  Экранировать нечего, инъекция невозможна в принципе;
- `timestamp` — это время события, добавленное плагином (`Time_Key`);
- поле `path` в схеме `input()` не описано, и оно просто отбрасывается —
  за это отвечает `input_format_skip_unknown_fields=1`, который плагин
  дописывает сам;
- три записи ушли одним запросом, и `GROUP BY` свернул их в **одну** строку
  таблицы. Агрегация случилась на вставке, до диска лишнее не доехало.

С `Table nginx_raw` вместо `Query` тело будет тем же, а запрос — просто
`INSERT INTO nginx_raw FORMAT JSONEachRow`.

## Записи → PostgreSQL

```ini
[OUTPUT]
    Name  postgres
    Match log.nginx
    Query INSERT INTO nginx_raw SELECT * FROM jsonb_populate_recordset(null::nginx_raw, $1)
```

Пачка приезжает **параметром `$1`** — массивом объектов jsonb (тоже реальный
захват):

```json
[{"timestamp":"2026-08-26T08:03:13.448931Z","host":"web-1","status":200,"bytes":1024,"path":"/api/v1/users"}]
```

Текст запроса при этом не меняется от вызова к вызову — сервер разбирает его
один раз, а данные приезжают отдельно.

## Метрики → любая из двух СУБД

У метрики нет «столбцов», поэтому она разворачивается в строку **фиксированной**
формы. Схему в запросе достаточно описать один раз, и она не зависит от того,
какие метрики придут:

```json
[{"name":"pg_database_xact_commit","type":"gauge","labels":{"instance":"postgres","database":"postgres"},"value":223,"timestamp":"2026-08-26T08:03:15.451962Z"},
 {"name":"pg_database_blks_hit","type":"gauge","labels":{"instance":"postgres","database":"postgres"},"value":301479,"timestamp":"2026-08-26T08:03:15.451962Z"}]
```

```ini
    Query INSERT INTO series SELECT timestamp, name, labels, value FROM input('name String, type String, labels Map(String,String), value Float64, timestamp DateTime64(6)')
```

Гистограммы и сводки пропускаются: у них не одно значение, а набор корзин, и в
плоскую строку они не ложатся.

## Выход, который ничего не отправляет

`out_ring` переворачивает картину: он не пушит, а копит. События ложатся в
кольцо на `Ring_Size` байт, старое вытесняется новым, а потребитель забирает
накопленное сам:

```
   конвейер ──> out_ring [ кольцо 64M, старое вытесняется ]
                              │
             GET /logs ───────┤ отдать, ничего не трогая
             GET /logs/clear ─┤ отдать и очистить
             GET /stats ──────┘ {"records":98,"bytes":15824,"dropped":911,…}
```

Выдача — те же JSON-строки, что и у остальных выходов:

```json
{"timestamp":"2026-08-26T08:03:13.448931Z","host":"web-1","status":200,"bytes":1024}
{"timestamp":"2026-08-26T08:03:13.949112Z","host":"web-2","status":500,"bytes":77}
```

Очистка происходит только при удавшейся отдаче, а одновременные запросы
сериализованы — из восьми параллельных всё заберёт первый, остальные получат
пусто. Плата за кольцо: плагин отвечает конвейеру «принято» сразу, поэтому
`Retry_Limit` и дисковый буфер эти данные не страхуют, а перезапуск fluent-bit
кольцо обнуляет.

## Метрики: забирают или отправляем сами

Два способа отдать метрики наружу, и оба уже есть в сборке — писать ничего не
нужно.

| | `prometheus_exporter` | `prometheus_remote_write` |
|---|---|---|
| как работает | слушает порт, prometheus приходит на `/metrics` | fluent-bit сам отправляет в prometheus |
| задержка | до следующего `scrape_interval` | до следующего `Flush` |
| кто с кем соединяется | prometheus → fluent-bit | fluent-bit → prometheus |
| нужен открытый порт | у fluent-bit | у prometheus |
| TLS | **нет** | есть (`Tls On`) |
| авторизация | **нет** | есть (`http_user` / `http_passwd`, `header`) |

Push настраивается так:

```ini
[OUTPUT]
    Name        prometheus_remote_write
    Match       metric.*
    Host        prom-1
    Port        9090
    Uri         /api/v1/write
    Tls         Off
    add_label   source fluent-bit
    storage.total_limit_size 256M
    Retry_Limit 5
```

На стороне prometheus нужен приёмник — он выключен по умолчанию:

```sh
prometheus --config.file=prometheus.yml --web.enable-remote-write-receiver
```

Проверено на стенде: prometheus запущен **без единой цели для scrape**
(`/api/v1/targets` → `активных целей: 0`), а метрики в нём есть — 17 рядов
`pg_*`, доставленных push-ом:

```
pg_database_xact_commit{database="postgres", instance="postgres", source="fluent-bit"} = 3
```

Метка `source` здесь от `add_label` — так помечают, чей это поток, когда в один
prometheus пишут несколько сборщиков.

Когда push уместнее pull:

- до fluent-bit не достучаться — NAT, закрытый сегмент, машина без входящих
  портов. Соединение устанавливает он сам;
- нужна задержка меньше интервала scrape;
- нужны TLS и пароль, которых у экспортёра нет вовсе;
- сборщиков много, а адреса их целей меняются — push избавляет от service
  discovery.

Когда лучше оставить pull:

- prometheus и так ходит по всей сети, и одна цель погоды не делает;
- важно видеть `up{}` — при push его нет, и молчащий источник надо ловить
  иначе (например `absent()` или `time() - max_over_time(...)`);
- приёмник remote write включать нельзя по политике.

Включать оба выхода разом не надо: метрики уедут дважды.

Тот же поток метрик принимают и `opentelemetry` (OTLP), и `influxdb` — вход
менять не нужно, только выход.

## Что произойдёт, если ошибиться

| ситуация | что будет |
|---|---|
| записи отправлены в `prometheus_exporter` | выход их не примет: он умеет только метрики |
| `Mode both` без `Metrics_Tag` | записи и метрики уедут под одним тегом и подерутся в выходе |
| поле записи не описано в `input()` (ClickHouse) | отбрасывается молча — так задумано |
| столбца нет в целевой таблице (PostgreSQL) | ошибка запроса; повтор не делается, пачка выбрасывается |
| приёмник недоступен | пачка возвращается в очередь, работают `Retry_Limit` и буфер |
| потребитель `out_ring` не приходит | кольцо заполняется и начинает терять самое старое — это его штатная работа |

## Гарантии доставки

Конвейер даёт **at-least-once**: при повторе после частично удавшейся вставки
строки могут задвоиться, а при исчерпании `Retry_Limit` — потеряться. Для
журналов это нормально (`ReplacingMergeTree` на стороне ClickHouse закрывает
дубли), для репликации таблицы — нет. Именно поэтому перегон таблиц делает
`pg2ch`, у которого отметка живёт в самой целевой таблице, а не в конвейере.

# Параметры

Пометка **«ядро»** — параметр обрабатывает сам fluent-bit, он одинаков у любого
плагина. **«наш»** — объявлен в плагине этого проекта. **«штатный плагин»** —
параметр апстримовского плагина.

Одноимённый параметр ядра перехватывается раньше и до плагина не доходит:
если параметр есть у ядра, у плагина его быть не может.


## `[SERVICE]` — параметры ядра

Секция одна на процесс, задаёт поведение самого fluent-bit.

| параметр | чей | что делает |
|---|---|---|
| `Flush` | ядро | как часто (секунды) конвейер отдаёт накопленное выходам. Это верхняя граница задержки, а не размер пачки: чанк уедет и раньше, если наполнится |
| `Grace` | ядро | сколько секунд на завершение при остановке: успеть слить буферы |
| `Daemon` | ядро | уйти в фон. В контейнере всегда `off` |
| `Log_Level` | ядро | `error`, `warn`, `info`, `debug`, `trace`. На `debug` наши плагины печатают число строк за прогон |
| `Log_File` | ядро | писать свой лог в файл вместо stderr |
| `Parsers_File` | ядро | файл с `[PARSER]`-описаниями; на них ссылается `Parser` у `tail` |
| `Plugins_File` | ядро | файл со списком внешних `.so`. **Обязателен** для наших плагинов: без него `Name postgres` — «плагин не существует». Штатный путь `/usr/local/etc/fluent-bit/plugins.conf` уже содержит все пять |
| `storage.path` | ядро | каталог для буферов на диске. Без него буфер только в памяти и при перезапуске теряется |
| `storage.sync`, `storage.checksum`, `storage.max_chunks_up` | ядро | режим записи буфера, контрольные суммы, сколько чанков держать в памяти |
| `HTTP_Server` | ядро | поднять служебный HTTP-интерфейс самого fluent-bit |
| `HTTP_Listen`, `HTTP_Port` | ядро | адрес и порт этого интерфейса (по умолчанию 0.0.0.0:2020). Отдаёт `/api/v1/metrics`, `/api/v1/health` |

Замечание про два порта: `HTTP_Port 2020` — это интерфейс **самого fluent-bit**
(жив ли он, сколько записей прошло). Порт `2021` в примерах — это уже
`prometheus_exporter`, то есть **ваши** метрики. Разные вещи.

К libpq-соединениям **не относятся**: там свои `Connect_Timeout` и `Conn_Options` |

## Общее для всех `[OUTPUT]` — параметры ядра

| параметр | чей | что делает |
|---|---|---|
| `Name` | ядро | плагин: `clickhouse`, `postgres`, `stdout`, `prometheus_exporter`… |
| `Match` | ядро | какие теги забирать. `*` — все, `pg.*` — по префиксу |
| `Match_Regex` | ядро | то же регулярным выражением, когда шаблона мало |
| `Alias` | ядро | имя инстанса в логах |
| `Host`, `Port` | ядро | адрес сервера. **Наши выходы берут адрес именно отсюда** (`ins->host`), своих `ch_target`/`pg_target` у них нет |
| `Retry_Limit` | ядро | сколько раз повторять неудавшуюся пачку: число, `no_limits` или `false`. Работает только для ответа `FLB_RETRY` (см. ниже) |
| `workers` | ядро | сколько потоков обслуживает выход. Для наших выходов больше одного — это несколько параллельных соединений к СУБД |

## Наши входы: `postgres` и `clickhouse`

Оба выполняют произвольный SQL по расписанию и кладут результат в конвейер.
Параметры общие, если не помечено иначе.

### Что и откуда брать

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Targets` | наш | — | список серверов через запятую: `host[:port]`. Один вход опрашивает **все** сразу. Порт по умолчанию 5432 / 8123 (8443 при `Tls On`). Пустой список — вход просто простаивает, это не ошибка: так гасится запрос к представлению, которого на этой установке нет |
| `Query` | наш | — | текст SQL прямо в конфигурации |
| `Query_File` | наш | — | файл с SQL. **Важнее, чем `Query`** |
| `User`, `Password` | наш | — | учётные данные. У `postgres` при Kerberos не нужны вовсе: имя берётся из билета. У `clickhouse` уезжают заголовками `X-ClickHouse-User` / `X-ClickHouse-Key` |
| `Database` | наш | — | база подключения (pg) или база по умолчанию для запроса (ch) |
| `Conn_Options` | наш (pg) | — | довесок к строке подключения libpq: `sslmode=require gssencmode=require` |
| `Interval_Sec`, `Interval_Nsec` | наш | `5` | период опроса |

### Форма результата

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Mode` | наш | `logs` | `logs` — запись на строку; `metrics` — gauge на числовой столбец; `both` — и то, и другое |
| `Instance_Field` | наш | `instance` | имя поля с именем сервера. Если запрос **сам** отдал столбец с таким именем (`hostName()` у ClickHouse), плагин своё не добавляет и берёт значение из результата — оно точнее адреса из `Targets`. Пусто — не добавлять |
| `Time_Field` | наш | — | столбец со временем события. Без него у записи будет время опроса, и порядок у получателя разъедется с порядком в журнале. Понимает `2026-08-24 12:00:00.123456+03`, ISO-8601 и epoch; без смещения считает UTC |

### Метрики (`Mode metrics` / `both`)

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Metric_Prefix` | наш | `pgsql` / `clickhouse` | общее начало имени: метрика зовётся `<префикс>_<столбец>` |
| `Label_Fields` | наш | — | столбцы-метки через запятую. `instance` добавляется сам. Значения меток — строки |
| `Value_Fields` | наш | — | столбцы-значения через запятую. Пусто — берутся **все** числовые, кроме меток, `Time_Field` и `Instance_Field`. Список стоит задавать явно: иначе метрикой станет случайное число вроде `pid` |
| `Metrics_Tag` | наш | — | тег, под которым уезжают метрики. Нужен при `Mode both`: один выход не примет и записи, и метрики |

### Инкрементальное чтение (`{CURSOR}`)

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Cursor_Field` | наш | — | поле результата, откуда берётся отметка. Плагин запоминает максимум по каждому серверу |
| `Cursor_File` | наш | — | путь-**основа** для хранения отметки между перезапусками. К нему дописывается `.<host>-<port>`: у каждого сервера свой файл, общий затирал бы соседний |
| `Cursor_Type` | наш | `datetime64` (ch) / `string` (pg) | в каком виде подставлять отметку в запрос: `datetime64`, `string`, `number`, `raw`. Таблица соответствий — ниже |
| `Cursor_Default` | наш | `now() - INTERVAL 30 SECOND` / `now() - INTERVAL '30 seconds'` | чем заменить `{CURSOR}` на самом первом запросе, когда отметки ещё нет. Подставляется **дословно, как текст SQL** |

### Как рендерится `{CURSOR}`

Подстановка проходит два разных пути, и их важно не путать.

**Первый запрос, отметки нет.** В `{CURSOR}` уходит `Cursor_Default` — без
кавычек, без приведения типа, `Cursor_Type` к нему не применяется вообще. Это
просто фрагмент SQL, который вы пишете на языке своей СУБД. Отсюда и умолчание
`now() - INTERVAL 30 SECOND`: оно осмысленно, только если курсор идёт по
времени. Для других столбцов его надо менять — `0` для `id bigint`, `''` для
текста, `'00000000-0000-0000-0000-000000000000'` для uuid.

**Дальше, отметка есть.** Вот тут работает `Cursor_Type`, и результат зависит
от плагина:

| `Cursor_Type` | `in_clickhouse` | `in_postgres` |
|---|---|---|
| `datetime64` | `toDateTime64('значение', 6)` — **по умолчанию** | `'значение'` — то же, что `string` |
| `string` | `'значение'` | `'значение'` — **по умолчанию** |
| `number` | `значение` | `значение` |
| `raw` | `значение` | `значение` |

`number` и `raw` рендерятся одинаково; разница в намерении. `number` — «это
число, кавычки испортят сравнение», `raw` — «обёртку допишу сам в тексте
запроса»: `WHERE id > '{CURSOR}'::uuid`. У второго есть ловушка: `Cursor_Default`
попадает в тот же слот, то есть внутрь ваших кавычек, — значит и его надо
писать без них.

**Что вообще может быть отметкой.** Плагин хранит её строкой не длиннее 127
байт (длиннее — молча обрежется) и сравнивает **строками**, через `strcmp`.
Из этого следует всё остальное:

«Сравнивает строками» — буквально: `id` со значением `12` превращается в
строку `"12"`, и максимум по пачке выбирается `strcmp`. Из пачки `1…12`
наибольшим окажется **`9`**, потому что `"9" > "12"` посимвольно. Дальше важно
не перепутать два разных последствия.

**Столбец числовой — это дубли, а не пропуск.** Отметка `9` уходит в запрос
числом, и база сравнивает честно: `WHERE id > 9` вернёт `10, 11, 12` ещё раз.
Проверено — вход по таблице `1…12` с `Cursor_Type number` напечатал:

```
тик 1:  id=1 id=2 id=3 id=4 id=5 id=6 id=7 id=8 id=9 id=10 id=11 id=12
тик 2:  id=10 id=11 id=12          ← те же строки второй раз
тик 3:  (пусто)                    ← курсор догнал, дальше тихо
```

Ничего не потеряно: конвейер и так `at-least-once`, а на следующем тике
отметка встаёт на настоящий максимум. Цена — лишнее чтение хвоста, тем
заметнее, чем крупнее пачка.

**Столбец текстовый — вот это уже потеря.** Если в `text` лежат числа,
лексический порядок становится порядком **самой базы**, и плагин ни при чём.
Проверено на том же стенде: курсор дошёл до `'9'`, после чего в таблицу
добавили `'10'`, `'11'`, `'12'` — и они не приехали никогда, потому что сам
PostgreSQL на `WHERE sid > '9'` отвечает нулём строк. Лечится не настройкой
плагина, а типом столбца или запросом (`ORDER BY sid::bigint`, `lpad`,
отдельный числовой ключ).

Отсюда практический вывод: годятся столбцы, у которых лексический порядок
совпадает с настоящим, — время в ISO-виде, uuid v7, `pg_lsn`, целые
одинаковой ширины. Для растущего `id` надёжнее схема `pg2ch`, где отметку
двигает не плагин, а сама база: `Cursor_Query` спрашивает `max(id)` у
приёмника.

Извлечение значения из ответа тоже разное. `in_postgres` берёт его через
`PQgetvalue`, то есть текстом, и подходит любой тип, кроме `NULL` — он строку
пропускает. `in_clickhouse` разбирает JSON и берёт **только строку или
неотрицательное целое**; `JSONEachRow` отдаёт строками почти всё, включая
64-битные целые и время, так что на практике этого хватает, но столбец типа
`Float64` отметку не сдвинет — она останется прежней, и каждый тик будет
перечитывать одно и то же. Пустая пачка отметку тоже не двигает, и это уже
специально.

### Прочее

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Buffer_Max_Size` | наш (ch) | `0` — без потолка | предел размера ответа. Менять не стоит: у HTTP-клиента fluent-bit ответ по умолчанию ограничен 4 КБ, и превышение — не обрезка, а ошибка всего запроса |
| `Connect_Timeout` | наш (pg) | `5` | таймаут подключения, секунды |
| `Statement_Timeout` | наш (pg) | `5000` | `statement_timeout` сеанса, миллисекунды: страховка от запроса, который повиснет на боевом сервере |
| `Retry_Pause_Sec` | наш (pg) | `30` | пауза после неудачного подключения. Без неё каждая попытка — ещё одно обращение к KDC |

## Наши выходы: `postgres` и `clickhouse`

Берут пачку событий и выполняют над ней **один** запрос. Значения в текст
запроса не подставляются: пачка едет отдельно, разбирает её сам сервер.

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Table` | наш | — | простая вставка: поля записи ложатся в одноимённые столбцы |
| `Query` | наш | — | произвольный SQL. **Важнее, чем `Table`.** В ClickHouse пачка доступна как `input('схема')`, в PostgreSQL — как параметр `$1` типа `jsonb` |
| `Query_File` | наш | — | то же из файла. **Важнее, чем `Query`** |
| `Time_Key` | наш | `timestamp` | под каким именем добавить в запись время события: в msgpack оно лежит отдельно от тела, а запросу нужно наравне с полями. Пусто — не добавлять |
| `Time_Format` | наш | `datetime64` (ch) / `iso8601` (pg) | `datetime64` → `2026-08-24 10:00:00.123456`, `iso8601` → `…T…Z`, `epoch` → число |
| `Skip_Unknown_Fields` | наш (ch) | `on` | не ронять вставку из-за полей, которым нет места в схеме. Выключать не стоит: поля записи и столбцы совпадают редко |
| `Settings` | наш (ch) | `date_time_input_format=best_effort` | настройки ClickHouse для вставки, `key=value` через запятую; уезжают параметрами URL |
| `Conn_Options` | наш (pg) | — | довесок к строке подключения libpq |
| `Connect_Timeout` | наш (pg) | `5` | секунды |
| `Statement_Timeout` | наш (pg) | `30000` | миллисекунды; больше, чем у входа: вставка пачки дольше опроса |

Про повторы. Ответ выхода решает судьбу пачки:

- `FLB_OK` — принято, чанк удаляется;
- `FLB_RETRY` — вернуть в очередь, подчиняется `Retry_Limit`;
- `FLB_ERROR` — выбросить сразу, повтор бессмыслен.

Наши выходы отвечают `FLB_ERROR` на 4xx от ClickHouse и на ошибки схемы/данных
от PostgreSQL: запрос неверен, повтор его не исправит, а место в буфере займёт.
Обрывы связи, нехватка ресурсов и 5xx уходят в `FLB_RETRY`.

## Насос `pg2ch`

Отдельный вход: гонит данные из PostgreSQL в ClickHouse, в конвейер кладёт
только запись-отчёт о прогоне.

| параметр | чей | по умолчанию | что делает |
|---|---|---|---|
| `Pg_Target` | наш | — | сервер-источник `host[:port]` |
| `Pg_User`, `Pg_Password`, `Pg_Database`, `Pg_Options` | наш | — | подключение к источнику; при Kerberos пароль не нужен |
| `Ch_Target` | наш | — | нода-приёмник `host[:port]` |
| `Ch_User`, `Ch_Password`, `Ch_Database` | наш | — | подключение к приёмнику |
| `Ch_Table` | наш | — | целевая таблица |
| `Ch_Columns` | наш | — | столбцы вставки в порядке `SELECT`, если порядок в таблице другой |
| `Ch_Settings` | наш | `date_time_input_format=best_effort` | настройки ClickHouse для вставки |
| `Query` / `Query_File` | наш | — | `SELECT` для `COPY`. `{CURSOR}` заменяется отметкой. **`ORDER BY` по столбцу отметки обязателен** |

| `Cursor_Default` | наш | `0` | отметка, когда цель пуста |
| `Batch_Bytes` | наш | `64M` | порог отправки батча. Каждая вставка — отдельный кусок MergeTree, поэтому мелкий батч при частом расписании плодит куски |
| `Report_Empty` | наш | `off` | писать отчёт и о прогонах, где строк не было |
| `Statement_Timeout` | наш | `0` — без ограничения | большой перегон дольше пяти секунд — это норма |
| `Retry_Pause_Sec` | наш | `30` | пауза после неудачного подключения |
| `Interval_Sec` | наш | `60` | период прогонов |

Штатный способ сделать метрику из потока записей — альтернатива нашему

| параметр | чей | что делает |
|---|---|---|
| `Match` | ядро | какие теги обрабатывать |
| `Tag` | штатный плагин | тег, под которым уедут получившиеся метрики |
| `Metric_Mode` | штатный плагин | `counter`, `gauge` или `histogram` |
| `Metric_Name` | штатный плагин | имя метрики |

блок**. Запрос с двадцатью счётчиками — двадцать блоков `[FILTER]`. Наш
`Mode metrics` берёт все числовые столбцы разом.

## Как проверить самому

Ничего из написанного ниже не нужно брать на веру: fluent-bit печатает
разбиение сам, разделяя `GLOBAL_OPTIONS` (ядро) и `OPTIONS` (плагин).

```sh
fluent-bit -e /usr/local/lib/fluent-bit/plugins/flb-in_postgres.so -i postgres -h
fluent-bit -e /usr/local/lib/fluent-bit/plugins/flb-out_clickhouse.so -o clickhouse -h
```

А `--dry-run` проверяет конкретную конфигурацию, не запуская сбор:

```sh
fluent-bit -c /usr/local/share/fluent-bit/examples/example.conf --dry-run
```

## Защита входящих соединений

Всё выше — про соединения, которые fluent-bit устанавливает **сам** (он клиент,
`Tls` включает шифрование до СУБД). Обратная задача — закрыть то, что слушает
сам fluent-bit. Здесь возможности сильно разные, и вот что проверено на живом
бинарнике 5.0.9:

| что слушает | TLS | авторизация |
|---|---|---|
| `in_forward` | да: `tls on` + `tls.crt_file`/`tls.key_file` | **да**: `shared_key` и `security.users <логин> <пароль>` |
| `in_splunk` | да | токен: `splunk_token` (формат Splunk HEC) |
| `in_http`, `in_opentelemetry`, `in_elasticsearch`, `in_tcp`, `in_syslog` | да | **нет** — TLS шифрует канал, но пускает любого |
| `prometheus_exporter` | **нет** — `tls on` отвергается: «does not support TLS» | нет |
| служебный интерфейс `HTTP_Server` (2020) | **нет** — таких параметров не существует | нет |

Отсюда практический вывод: **своей авторизацией по логину и паролю обладает
только `forward`**. Всё остальное закрывается обратным прокси.

### Вариант 1: forward — TLS и пароль без всякого прокси

```ini
[INPUT]
    Name           forward
    Listen         0.0.0.0
    Port           24224
    tls            on
    tls.crt_file   /etc/fluent-bit/ssl/server.crt
    tls.key_file   /etc/fluent-bit/ssl/server.key
    shared_key     ${FLB_SHARED_KEY}
    self_hostname  ${HOSTNAME}
    security.users kolya parol-koli
```

Клиент (`out_forward`) обязан предъявить и общий ключ, и пару логин/пароль:

```ini
[OUTPUT]
    Name          forward
    Match         *
    Host          collector
    Port          24224
    tls           on
    Shared_Key    ${FLB_SHARED_KEY}
    Self_Hostname ${HOSTNAME}
    Username      kolya
    Password      parol-koli
```

Проверено: верный пароль — записи идут; неверный пароль или неизвестный
пользователь — рукопожатие обрывается, в конвейер не попадает ничего.
`security.users` можно писать несколько раз, по строке на пользователя.

### Вариант 2: всё остальное — за обратным прокси

Схема простая: fluent-bit слушает **только петлю**, наружу
смотрит nginx, он же терминирует TLS и спрашивает пароль.

```
клиент ──TLS+пароль──> nginx :8443 ──открытый HTTP──> 127.0.0.1:2021 (метрики)
                                                      127.0.0.1:2020 (служебный)
                                                      127.0.0.1:9880 (in_http)
```

Проверено: без пароля прокси отвечает `401`, с паролем — отдаёт метрики и
служебный интерфейс. В этом же проекте собран nginx с модулем SPNEGO
(`dmp/nginx:*-spnego`) — тогда вместо пароля работает доменный билет Kerberos.

Третий путь для метрик — вообще ничего не слушать: `prometheus_remote_write`
сам отправляет метрики в prometheus (выход `prometheus_remote_write`), и тогда
открытого порта не остаётся.

### Про `tls.verify` и клиентские сертификаты

Если однажды понадобится пускать по сертификату, а не по паролю: у входов есть
`tls.verify_client_cert on` вместе с `tls.ca_file`. Ловушка проверена
экспериментом: **при `tls.verify off` проверка клиентского сертификата молча не
работает** — соединение без сертификата проходит насквозь. Нужны обе строки:
`tls.verify on` и `tls.verify_client_cert on`.

## Ловушки, которые стоят отдельного упоминания

- **Одноимённый параметр ядра побеждает.** `Tls`, `Host`, `Port`, `Match`,
  `Tag`, `Alias`, `Retry_Limit`, `storage.*` до плагина не доходят.
- **Неизвестный параметр — ошибка запуска.** Опечатка в имени не будет
  проигнорирована: fluent-bit откажется стартовать. Это удобно — проверяется
  через `fluent-bit --dry-run`.
- **Пустая переменная окружения = параметр не задан.** `Password ${CH_PASSWORD}`
  при пустом значении означает «без пароля», а не «пароль — пустая строка».
- **`Plugins_File` обязателен.** Без него наши плагины не загружены, и
  `Name postgres` — «плагин не существует». При запуске флагами командной
  строки вместо файла нужен `-e /usr/local/lib/fluent-bit/plugins/flb-*.so`.
- **Метрики и записи не смешиваются в одном выходе.** `prometheus_exporter`
  принимает только метрики; при `Mode both` разводите их `Metrics_Tag`.
- **`Flush` — не размер пачки, а верхняя граница задержки.** Размер пачки
  определяется тем, сколько успело накопиться.
- **Значение — всегда одна строка.** Перенос длинного SQL — ошибка
  `extra indentation level found`; для длинного запроса есть `Query_File`.
- **Неизвестный ключ в `[SERVICE]` НЕ проверяется.** В отличие от свойств
  плагинов, опечатка или выдуманный ключ в `[SERVICE]` молча игнорируется, и
  `--dry-run` скажет «successful». Именно так выглядит попытка включить
  несуществующий TLS у служебного интерфейса.
- **В командной строке `-p` относится к последнему объявленному плагину.**
  `-i clickhouse -o null -p tls=on` задаёт `tls` **выходу** `null`, а не входу.
  Свойства входа пишутся до `-o`.
